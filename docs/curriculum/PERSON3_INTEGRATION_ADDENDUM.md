## 2. Integration boundary (D)

* The canonical graph stores **curriculum facts only**: concepts, typed
  relationships, provenance, review state, version history.
* **Never** stored: mastery probabilities, learner histories, AKT predictions,
  BKT parameters, model/calibration data. These remain Person 3's domain and
  reach the adapter only as *function arguments* (e.g. the `mastery_vector` of
  `evaluate_prerequisite_readiness`), never as persisted graph state.
* A learner-state record's `concept_id` (contract
  `learner_state_schema.json`) must resolve to a canonical id:
  `KnowledgeGraphAdapter.resolve_concept_id()` forwards merged/replaced historical
  ids to their successor; an id that resolves to nothing raises `KeyError` from
  traversal methods and returns `None` from `get_concept`. There is no implicit
  aliasing and no display-name matching at this boundary.

## 3. ID policy

| Namespace | Example | Canonical? |
|---|---|---|
| Canonical concept ids | `cc_657f849a43943675` | Yes — `cc_<sha256(curriculum_id::stable_key)[:16]>`, frozen at creation, independent of display names |
| Simulator / AKT vocabulary ids | `PHY_KIN`, `CHE_EQM` | **No** — external references only; valid in learner state *only* paired with an explicit mapping entry |
| Historical ids | tombstoned `cc_*` | Resolve forward via `graph.id_map` (`merged_into` / `replace_with`); `removed` resolves to nothing |

The AKT vocabulary (`akt_vocabulary.json`, 62 concept ids) and all three Person 3
concept CSVs (v3 / v4 / confirmatory — verified identical: same 62 ids, names and
prerequisite lists) share one id space, none of which is the canonical space.

## 4. Simulator → canonical mapping (F)

Mapping runs through the existing `curriculum/simulator.py` `SimulatorBridge`
(never display-name-only):

* **override** (explicit reviewed id map) beats the rule table;
* otherwise rules **R1–R5** against canonical names/aliases
  (ACCEPTED ≥ 0.90 with a decisive margin, 0.60–0.90 → `ambiguous`, else `unmapped`);
* outcomes are exactly `mapped` / `ambiguous` / `unmapped` / `excluded` —
  **no concept or edge is silently dropped**: unmapped ids appear verbatim in the
  report's `unmapped` buckets and `unmapped_ids` list, and no mapping ever targets
  a deprecated canonical concept;
* the original simulator id is preserved as the mapping's key (external
  reference) alongside the resolved canonical id;
* prerequisite edges are checked only when *both* endpoints mapped; unmapped-endpoint
  edges are reported as `unchecked`, never assumed compatible.

Overrides are **inputs** (`--overrides file.json`), not hidden defaults; an
override naming an unknown canonical id is reported as a failure reason, not applied.

## 5. Direction semantics

Convention everywhere: **`A --prerequisite_of--> B` = A must be learned before B**,
so `get_direct_prerequisites(B) → [A]`. Person 3 stores the inverse index on the
node (`B.prerequisite_concept_ids = [A]`), which is the same relation. This was
verified mechanically, id for id across all 62 concepts, against Person 3's actual
`src/knowledge_graph.py` (direct prerequisites/dependents, transitive closures,
precedence, cycles, readiness, remediation — `test_person3_reference_equivalence.py`).

## 6. Graph versioning

`adapter.curriculum_id`, `adapter.syllabus_version` and
`adapter.graph_fingerprint()` (the canonical content fingerprint) are exposed so a
consumer can detect a changed canonical graph and refuse stale inputs. An
incompatible request — `from_repository(repo, "unknown_id")` — raises
`CanonicalGraphUnavailableError` naming the curricula actually held. Concept ids
never change with renames or version snapshots (covered by tests).

## 7. Fallback policy (E)

* **Integrated mode has no CSV path.** `KnowledgeGraphAdapter` has no default
  constructor argument, rejects non-`CurriculumGraph` inputs with `TypeError`, and
  `from_repository` raises `CanonicalGraphUnavailableError` (message includes the
  remedy) when no canonical graph is stored. Nothing on disk is created by the
  failed load.
* CSV/synthetic fixtures remain allowed **only** for isolated unit tests and
  explicit simulator/demo mode (`curriculum/simulator.py` reads the simulator CSV
  as read-only *input* to mapping — it never becomes the graph).
* Adapter operations are read-only: a query battery over a tmp store leaves the
  graph fingerprint, the file tree and the API `/status` payload byte-identical
  (asserted in both unit and integration tests).

**Adapter surface (Person 3 method names preserved):** `get_concept`,
`get_node` (minimal node view exposing `to_contract_dict()`, added so Person 3's
adapter can wrap this adapter without code changes), `get_prerequisites`/`get_direct_prerequisites`,
`get_dependents`/`get_direct_dependents`, `get_all_ancestor_prerequisites`,
`get_all_descendant_dependents`, `contains`, `concept_ids` (property),
`get_all_concept_ids`, `topological_sort`, `detect_cycles`,
`find_invalid_prerequisite_references`, `validate_graph`,
`evaluate_prerequisite_readiness` (same 3-tuple + `satisfied|unsatisfied|unknown`
semantics), `get_remediation_sequence`.

**Documented deviations** (interface changes, kept minimal and tested):
1. `get_concept` returns the shared `concept_schema.json` record
   (`to_contract_record()`), not Person 3's `ConceptNode` dataclass — Person 2
   does not import or mirror Person 3's models.
2. `validate_graph()` returns Person 2's structured `GraphValidationReport`
   instead of raising `ValueError` (`report.is_valid` is the verdict).
3. `topological_sort()` raises `curriculum.graph.PrerequisiteCycleError` (canonical
   guard) instead of `RuntimeError`.
4. Canonical-only additions: `resolve_concept_id`, `graph_fingerprint`,
   `curriculum_id`, `syllabus_version`, `accepted_only`.
5. Traversal policy: **accepted (reviewed) edges only** by default — an unreviewed
   extraction guess must not gate a learner's path — and deprecated concepts are
   readable via `get_concept` but excluded from traversal (`KeyError` if queried),
   matching the adapter's "inspect history, don't learn from it" stance.

### Post-audit fix — `get_node` duck-compatibility (2026-10-23)

Independent re-audit of Person 3's pipeline (`src/integration/pipeline.py`) showed
that `IntegratedLearningLoopPipeline.__init__` constructs
`KnowledgeGraphAdapter(graph=self.knowledge_graph)` (Person 3's adapter) and calls
`self._graph.get_node(concept_id)` inside its `get_concept`. The canonical adapter
did not expose `get_node`, so wiring a canonical adapter into Person 3's pipeline
raised `AttributeError: ... has no attribute 'get_node'`. Reproduced before the
fix; resolved by adding `_CanonicalConceptNode` (a minimal view exposing only
`to_contract_dict()`) and `KnowledgeGraphAdapter.get_node()`, which resolves
historical ids forward and returns `None` for unknown ids. Person 3's code is
unchanged. Regression coverage:
`test_get_node_exposes_contract_record_for_person3_wrapping` and
`test_person3_adapter_and_engines_wrap_canonical_adapter`.

## 11b. Threshold semantics (blocker D)

These are distinct quantities and must not be conflated:

| Name | Value | Where used | Meaning |
|---|---|---|---|
| `DEFAULT_MASTERY_THRESHOLD` (inference) | 0.70 | `src/akt_inference.py` | Minimum calibrated mastery probability to consider a concept *mastered* for workflow decisions. |
| Graph readiness threshold | 0.50 | `src/knowledge_graph.py` `evaluate_prerequisite_readiness`, `src/recommendation.py` line 134 | Minimum mastery for a *prerequisite* to be considered satisfied. |
| Unmastered-selection threshold | 0.75 | `src/recommendation.py` lines 122, 393, 401 | Below this, a concept is treated as unassessed/weak for advancement selection. |
| Calibrated mastery prior | 0.35 | `src/akt_inference.py` `calibrate_mastery_probability` | Cold-start prior for unassessed concepts. |

Decision required (team): whether to unify 0.50/0.70/0.75 or keep per-context. Values are unchanged pending authorization.
